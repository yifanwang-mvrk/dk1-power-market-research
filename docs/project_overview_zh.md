# DK1 项目，从零到完成

**入门概览 | DK1 Short-Term Power Market Research | 2026-09-04**

这份概览帮助你理解全局：我们研究什么、为什么按这个顺序做、每一步留下什么成果。它沿用冻结的 Blueprint，详细定义仍以 `docs/project_handbook.md` 为准。

## 1. 我们究竟要做出什么？

我们要建立一个能用证据回答问题的研究项目：**当风电、光伏的预报更新时，这些新信息是否有助于判断 DK1 短期电力系统的平衡压力？哪些时候有用，哪些时候会失效？**

DK1 是丹麦西部电力市场区域。我们先研究这一个区域，以一个交割小时为一个观察对象。

你可以把最终成果想成一份“有数据依据的市场判断”：当时看到了什么信息；为什么形成这个方向判断；历史证据支持到什么程度；什么会推翻判断；后来发生了什么。

项目完成后，应能拿出五类东西：

1. **可信的数据底表**：每小时的数据能对齐，来源和发布时间说得清。
2. **研究证据**：H1/H2/H3 的测试、图表、结果与局限。
3. **可解释的判断规则**：何时偏向 UP、DOWN，何时选择 No Trade。
4. **诚实的成绩单**：与简单基准、最终未见数据的比较。
5. **可以展示和讲解的材料**：README、研究 memo、Market State Card 与复盘日志。

成功标准是把研究做完整并讲清楚。即使结果是“没有发现超越基准的信号”，仍然是有效成果。当前研究不声称实际交易盈利。

## 2. 用一个小时，把整件事看明白

**下面全部是虚构教学数字，不是已下载的数据、实际结果或项目正式参数。**

假设我们研究某天 15:00-16:00 的电力交割：

| 时间或信息 | 教学例子 | 我们怎么理解 |
|---|---|---|
| 日前参考价已确定 | 50 EUR/MWh | 后面用它衡量平衡价格相对高还是低 |
| 5h horizon 的风电预报 | 3,000 MW | 对这个交割小时较早的预期 |
| 1h horizon 的风电预报 | 3,400 MW | 对同一个交割小时较新的预期 |
| 两个预报都已发布后 | Revision = +400 MW | 预期风电比之前更多；具体决策时点仍须核实 |
| 交割后的结果公布 | Balancing price = 42 EUR/MWh | 事后才能用于评分，不能倒填成决策信息 |

**先形成假设：** 风电预期增加，系统可能比原先预想的更宽松，因此更可能出现向下压力。这里的“可能”需要检验；跨境条件、需求或市场已经吸收信息，都可能改变关系。

**再定义结果：** Spread = 42 - 50 = -8 EUR/MWh。假设教学用的中性带 δ = 5，则该例标签为 DOWN，因为 -8 < -5。

真实项目的 δ 不是 5。它将按冻结规则，用开发期非零绝对 spread 的第 25 百分位数计算，当前尚未算出。

**最后问：** 如果我们在很多历史小时里都这样判断，是否真的比简单办法更好？哪些情况下会错？单独这个例子不能证明假设成立。

整个项目可以记成：**新信息 → 有理由的假设 → 历史检验 → 有条件的判断 → 结果与复盘。**

## 3. 从零开始的八个阶段

下面的“阶段一至八”是便于理解的阅读顺序；括号里的 P 编号是原执行手册的工作地址，没有重新编号。

| 阶段 | 我们干什么 | 交付什么 | 怎样算完成 |
|---|---|---|---|
| 一：确定问题与工作规则（P0） | 固定范围、目标、日期和记录方式；建立仓库与环境 | 控制三件套、仓库、研究配置和 Charter | 知道研究什么、什么不能提前看、成果存哪里 |
| 二：确认数据能不能用（P1） | 查字段定义、历史覆盖、发布时间，验证 forecast horizon | 数据字典、来源证据、可用与不可用清单 | 能证明每个字段是什么、当时是否能知道 |
| 三：把数据整理成底表（P2） | 下载开发期数据，保存原始数据，统一时间和单位，再合并 | 原始数据、每小时底表、质量检查结果 | 不同数据指向同一个小时，缺失和重复解释清楚 |
| 四：规定什么算判断对（P3） | 计算 spread、δ 和三类标签，建立简单基准 | 标签表、冻结的 δ、类别分布和基准定义 | UP / DOWN / NEUTRAL 含义明确，评分不临时改 |
| 五：逐个检验市场想法（P4/P5/P6） | H2 先做；再看 H1 的系统条件和 H3 的跨境影响 | 假设测试、图表、书面结论与失败条件 | 每个研究问题都留下证据，支持或 null 均可 |
| 六：把证据变成判断（P7） | 形成透明规则、置信度、风险与 No Trade 条件 | 信号规则、Market State Card、市场日志 | 能解释某次判断的依据，也能解释何时不判断 |
| 七：整理可展示的成果（P8/P9） | 对照 Level A/B 验收，写 README 和研究 memo | 证据齐全的公开说明和可讲解案例 | 陈述与已完成工作一致，能独立解释结果和局限 |
| 八：做最终未见数据检验（P10） | 开发期内完成 Logistic Regression 与校准；冻结规格后解锁 holdout | 最终成绩单、基准比较、校准与局限报告 | Level C 全部满足；表现差也如实保留 |

**为什么不能直接下载数据就建模型？** 因为模型之前必须知道目标是什么、信息当时是否可得、数据能否对齐、怎样比较才公平。前四阶段给后面的研究提供可信基础。

## 4. 三个假设，以及成果如何逐步长出来

### H2：新预报是否带来了有用信息？

我们先研究这个核心问题：同一交割小时的 wind / solar 预报，从 5h 更新到 1h 后发生了什么变化？这种变化是否与 balancing pressure 有关系？

交付：真实配对的 revision 变量、一轮测试、图表、结论，以及哪些情况下关系不成立。具体数据结构必须先过 P1.1。

### H1：系统原本紧不紧，会不会影响判断？

Residual load 可以直观理解为：需求减去风电和光伏后，还需要其他供给承担多少。

H1-A 使用事后实际数据解释物理机制。H1-B 只有在找到当时可得的输入后，才可参与判断。**事后知道的事情，可以解释过去，却不能伪装成当时已经知道。**

交付：机制图和结论；如有合格输入，再形成可用于决策的 residual-load proxy。

### H3：跨境条件会不会改变 H2 的作用？

DK1 的状态可能受到跨境交换及系统条件影响。我们检查同样的 forecast revision，在不同条件下是否表现不同。

交付：条件分组的结果和局限。事前未知的实际流量只能用来解释，不能偷偷放进预测。

### 三个里程碑，是证据门槛

| 里程碑 | 你可以怎么理解 | 必须已有的关键证据 |
|---|---|---|
| Level A：CV-safe | 已经做出一项真实、可以核查的研究成果 | 仓库与文档、配置、三类核心数据、字典、H2 revision、至少一次完整测试和结论、一张图；holdout 未使用 |
| Level B：Interview Ready | 能讲清从信息到判断和风险的全过程 | 完整 H2、H1 机制、H3 初步条件研究、规则、confidence、风险、卡片、日志、memo 和两个基准 |
| Level C：MVP Complete | 完整研究经过事前保留数据的检验 | Logistic Regression、按协议解锁的 holdout、样本外比较、校准、regime 表现、局限和最终文档 |

**Level A 可以先达到。** 完成 H2 的首次真实测试并满足 A 的全部条件后，可先进入 P8；不必等 H1/H3 或整个模型流程结束。随后继续完成 B 和 C。

## 5. 怎么知道结果可信？

### 第一条：把已知信息与事后答案分开

预报值也要检查何时发布；actual wind、actual demand、final balancing price 等不能因为在历史表中存在，就自动获得决策资格。我们会保存决策时点可用的信息快照。

### 第二条：用简单办法当对手

**Majority baseline**：训练期最多见哪个类别，就总猜那个类别。

**Persistence baseline**：用上一小时的 pressure 类别预测下一小时。上一小时的标签也必须核实发布时间；若当时尚不可得，就不能把这个事后参考基准当成可实施判断。

假设某个方法准确率 60%，这本身不够。还要知道简单基准表现多少、各类别表现如何、它是否只挑了容易判断的小时。

### 第三条：保留一份开发时不看的“考卷”

| 区间 | 日期 | 用途 |
|---|---|---|
| 开发期 | 2022-01-01 至 2024-06-30 | 理解数据、计算 δ、研究假设、定义规则、开发和校准模型 |
| 锁定留出期 | 2024-07-01 至 2024-12-31 | Level C 冻结规格后才解锁，检验最终结果 |

这个“考卷”类比只用于理解数据隔离。Holdout 不能先看分布再改特征，也不能试完后挑一个最好看的版本当原始结论。

### 第四条：判断方向和决定参与分开

UP / DOWN / NEUTRAL 是结果分类；Bullish / Bearish / No Trade 是研究决策。信息不足或信号冲突时选择 No Trade，本身也要写出理由。

## 6. 怎样学，才不会再次失去全局？

### 建议一：按三层阅读，不从头背手册

**先读这份概览**，理解全链条；**每次工作先看 Status**，知道当前步骤；**做到具体步骤再查 Handbook** 的对应定义。Decision Log 在你想知道“为什么当时这样定”时使用。

### 建议二：每次工作只回答一个业务问题

例如 P1.1 的问题是：“同一交割小时的 5h 与 1h 预报，历史上真的存在，而且当时已经可用吗？”先说清问题，再操作数据和代码。

每次开工固定四句：**现在在哪一步；这一步回答什么；今天交付什么；什么证据出现后才能进入下一步。**

### 建议三：用同一个小时贯穿整个项目

在 P1/P2 确认数据后，选一个真实 development 小时，跟着它看原始字段、修正值、标签、规则判断和复盘。这个小时用于学习链条；正式结论仍要依据完整测试，不能只靠一个成功案例。

### 建议四：每一步做一次一分钟复述

不用背代码，尝试回答：输入是什么？输出是什么？为什么这样做？最容易错在哪里？如果讲不清，先回到这个小问题，再继续下一步。

### 建议五：让每次工作留下可见成果

可以是一页字段解释、一张对齐后的表、一幅带结论的图，或一张状态卡。把文件和结论记入 Status，再写下一次唯一动作。这样你看到的是研究成果逐步累积，而不只是代码越来越多。
